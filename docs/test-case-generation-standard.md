# CasePilot 用例生成规范

本文档定义 CasePilot 从需求分析到候选用例质量检查的统一生成契约。生成结果始终是候选，用例只有在用户明确确认后才能进入正式集合。

## 1. 标准结构

每条用例的正文只包含四个部分：

```json
{
  "title": "验证码过期后登录失败",
  "test_setup": [
    "用户已进入验证码登录页",
    "准备一个已超过有效期的验证码"
  ],
  "test_procedure": [
    "输入手机号和已过期验证码",
    "点击登录"
  ],
  "test_validation": [
    "手机号和验证码可被提交，页面不提前中断操作",
    "登录请求失败并提示验证码已过期，不创建登录会话"
  ]
}
```

`module`、`priority`、`case_type`、`tags`、测试点引用和证据引用属于管理与追踪元数据，不改变四段式正文。

## 2. 字段规则

### title

- 必填，描述一个明确的测试目标和场景。
- 一条用例只验证一个核心目标。
- 不写执行过程，不使用“功能测试”“验证正常”等泛化名称。

### test_setup

- 必填，使用有序字符串列表。
- 只描述执行前已经成立的环境、状态、身份、权限和测试数据。
- 不把操作步骤或期望结果写进 setup。
- 无额外前提时填写 `无特殊前置条件`，不得留空。

### test_procedure

- 必填，包含 1 至 4 个按执行顺序排列的操作。
- 每项以明确动作和对象为中心，测试人员可独立执行。
- 不混入“应该”“成功”“显示”等结果性描述。

### test_validation

- 必填，数量必须与 `test_procedure` 完全一致，并按索引一一对应。
- 每项说明可观察、可判定的页面、接口、数据、事件、状态或副作用结果。
- 禁止只写“正常”“正确”“符合预期”。
- 未被需求或证据确认的阈值、文案和业务规则必须标记为假设，不能写成确定事实。

## 3. 生成流程

1. 明确测试对象；只有测试对象缺失时才暂停并询问。
2. 分析需求、风险、约束和假设，并保留证据引用。
3. 建立 `需求 → 功能点 → 测试点 → 候选用例` 引用链。
4. 按四段式规范生成候选用例，覆盖已确认的主流程及重要边界、失败、恢复、权限、状态和并发风险。
5. 执行结构、可执行性、可观察性、重复性、引用和证据质量检查。
6. 质量检查失败时最多定向返修两轮；仍失败则阻止发布正式资产。
7. 用户明确确认后，才将候选写入正式集合并创建可追溯 Revision。

## 4. 兼容映射

当前持久层继续使用原有字段，生成与展示层按下列规则映射：

| 标准字段 | 内部兼容字段 |
| --- | --- |
| `title` | `title` |
| `test_setup` | `preconditions` |
| `test_procedure[n]` | `steps[n].action` |
| `test_validation[n]` | `steps[n].expected` |

该映射只用于兼容现有 API 和历史数据，不允许生成过程退回“一步一个混合操作/校验块”的表达方式。

## 5. 发布门禁

以下任一情况会阻止候选进入正式集合：

- 四个正文部分缺失或为空；
- procedure 与 validation 无法按索引一一对应；
- 操作不可执行或断言不可观察；
- 测试点、功能点或需求引用无效；
- 存在阻断级重复、来源越权或无依据的确定性规则。
