# CasePilot 产品功能 Review V2.2

> 日期：2026-07-28
> 范围：AI 用例生成、候选评审、用例管理、知识来源、Revision 与 QA 执行交接
> 场景：豆包 App 实时语音通话

## 1. Review 结论

CasePilot 已具备“需求输入 → 分阶段生成 → 候选评审 → 人工写入 → 用例管理”的真实数据闭环。当前最需要优化的不是增加更多一级页面，而是让生成前的输入更具体、生成后的去向更明确，并保证本地 Mock 验收能返回与业务领域一致的结构化用例。

本轮更新：

- 首次生成页加入“豆包实时语音通话”完整需求模板。
- Mock Agent 识别实时语音领域，生成 8 条覆盖权限、插话、弱网、路由、中断和隐私的候选用例。
- 候选写入成功后提供“前往用例管理”主交接动作。
- 用例管理继续以集合、搜索、列表/脑图和 Revision 详情为单一资产真值。
- Figma 以当前代码视觉和交互为准，补充首次生成、候选评审、写入后管理与用户动线。

## 2. 主要发现

| 优先级 | 发现 | 影响 | 本轮决策 |
| --- | --- | --- | --- |
| P0 | 旧产品文档仍写着 AI 未启用 | 与真实 Generation Job、知识库和 Worker 冲突 | 以当前代码和 API 为真值 |
| P0 | 通用 Mock 只能生成“核心业务/幂等”两条用例 | 无法验收具体产品需求 | 增加实时语音领域生成 |
| P1 | 写入成功后只显示提示，没有下一步 | 用户需重新寻找用例管理入口 | 增加直达用例管理 CTA |
| P1 | 首次页示例过于抽象 | 用户仍需自己组织完整需求 | 加入可编辑的领域模板 |
| P1 | Figma 是旧蓝白基础变量，部分 code syntax 拼写错误 | 设计与实现不可追踪 | 修正变量并新增现行画面 |
| P2 | 知识来源列表在数据多时占据较大空间 | 首次任务焦点被稀释 | 后续增加折叠和搜索，不阻塞本轮 |

## 3. 更新后的核心动线

```mermaid
flowchart LR
  A[进入 AI 用例工作台] --> B[选择目标用例集]
  B --> C[套用或编辑豆包语音需求]
  C --> D[开始生成]
  D --> E[查看阶段进度与开放问题]
  E --> F[在脑图或列表评审候选]
  F --> G[逐条纳入、排除或编辑]
  G --> H[人工确认写入]
  H --> I[前往用例管理]
  I --> J[搜索并查看结构化详情]
  J --> K[编辑后保存为新 Revision]
```

## 4. 页面与交互规范

### 4.1 首次生成

- 主任务只有一个：把需求变成候选用例。
- 目标用例集、模型和知识来源在提交前可确认。
- 领域模板只填充输入框，不自动提交，用户保留最终控制权。
- 明确提示候选内容不会直接写入正式资产。

### 4.2 候选评审

- 分阶段进度展示真实 Generation Job 阶段。
- 候选与正式用例在编号、标签和写入动作上清晰区分。
- 支持脑图和列表读取同一批候选。
- 写入前可全选、清空、逐条排除或编辑。
- 质量评分和开放问题是辅助信息，不能替代人工确认。

### 4.3 用例管理

- 写入完成后提供明确交接动作。
- 列表、脑图和详情读取同一 Revision。
- 搜索覆盖标题、编号、模块和标签。
- 编辑生成新 Revision，不覆盖历史版本。
- QA 执行结果只属于具体执行任务，不回写为资产状态。

## 5. 验收标准

- 一键填入豆包实时语音通话需求，但不会自动提交。
- 生成结果至少覆盖通话建立、麦克风权限、插话、弱网重连、断网、音频路由、系统中断和资源释放。
- 候选必须先人工确认，写入后才成为正式用例。
- 写入成功后可一步进入用例管理。
- 在目标集合中可搜索到新用例并查看前置条件、步骤、校验点和来源。
- 页面刷新后正式用例仍存在。
