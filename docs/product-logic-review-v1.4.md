> 结论：本轮界面与核心交互逻辑通过；数据持久化与真实 AI Provider 仍按开发基线推进。

## 1. 已统一的关键决策

| 主题 | 统一结论 | 当前实现 |
|---|---|---|
| 产品入口 | 当前自部署验收先登录本地账号 | 登录后进入默认质量空间 |
| 资产边界 | 空间 → 用例集合 → 用例 | 全局对话可创建集合，集合工作台只编辑当前集合 |
| 模型选择 | 首页和集合工作台共享一个 `model_id` | 自动选择、Test Design Pro、本地模型 |
| 生成任务 | 模型选择属于任务输入快照 | Web 请求和 API `input_payload` 保存 `model_id` |
| AI 结果 | AI 只能生成 Pending 候选 | Mock 输出固定为 Pending |
| 用例状态 | 只有五种用户可见状态 | Pending、通过、不通过、跳过、堵塞 |
| 评审 | 评审是事件，不形成第二套状态 | 提交评审、评论和决定后续写入 `review_events` |
| 多视图 | 脑图、列表、详情和文档读取同一用例状态 | 当前由 `workspaceCases` 单一前端状态驱动 |
| 状态汇总 | 五种状态分别统计，不再合并为“风险” | 脑图图例与节点图标已同步 |
| 服务健康 | 正常状态不常驻顶部 | 仅异常时设计故障提示 |
| 底部操作 | 浮动控件必须有安全间距 | 脑图工具栏、图例、输入和详情页脚已统一 |
| 测试执行 | 执行结果不覆盖用例状态 | 独立 `execution_status`、步骤确认、实际结果和缺陷引用 |

## 2. 端到端逻辑检查

### 2.1 登录与空间

`登录 → 获取账号与空间 → 进入默认空间 → 切换空间 → 刷新空间资产`

- 当前登录、会话保持和默认空间可验收。
- 空间切换后的集合与用例仍使用前端模拟数据；正式版本必须按 `space_id` 重新拉取。

### 2.2 创建与生成

`全局对话/集合管理创建入口 → 确定集合 → 选择模型 → 输入或上传 → 创建 Generation Job → SSE 进度 → Pending 用例`

- 两个创建入口最终都进入集合工作台。
- 模型选择跨页面保持，并进入任务输入。
- 空输入和重复提交已有前端保护。
- 文件解析、取消、断点续作仍属于后续里程碑。

### 2.3 用例编辑与状态

`选择脑图或列表用例 → 查看详情 → 修改/AI 候选 → 人工接受 → 新 Revision → Pending → 人工设置状态`

- 五种状态已经共享同一视觉组件和详情下拉菜单。
- 当前状态变更是前端内存操作；正式实现必须调用状态事件 API，并要求不通过、跳过、堵塞填写原因。
- 已通过用例接受 AI 改写时，正式实现必须创建新 Revision 并回到 Pending，不能覆盖旧 Revision。

### 2.4 评审与发布

`提交评审 → 分配评审人 → 评论/决定 → case_status 更新 → 发布集合 Baseline`

- 当前“提交评审”仍打开账号面板，属于占位行为，不是最终评审实现。
- 正式验收前需要独立评审面板、Reviewer 权限、批量影响预览和发布门禁。

### 2.5 测试说明

`同一结构化数据 → 脑图 / 列表 / 详情 / 测试说明 → 导出`

- 当前四个视图共享用例数组，状态展示已统一。
- Markdown/JSON 导出可演示；DOCX、PDF、XLSX 和版本发布尚未实现。

## 3. 五状态规范

| 中文 | API 值 | 颜色 | 允许来源 | 典型后续 |
|---|---|---|---|---|
| Pending | `pending` | 黄 | AI、导入、新建、新修订 | 进入任一状态 |
| 通过 | `passed` | 绿 | 人工确认 | 新修订后回 Pending |
| 不通过 | `failed` | 红 | 人工判定 | 修改后回 Pending |
| 跳过 | `skipped` | 紫 | 人工选择 | 重新纳入后回 Pending |
| 堵塞 | `blocked` | 橙 | 人工或依赖检查 | 解除后回 Pending |

状态不能只靠颜色识别；所有视图必须同时显示文字和状态圆点。状态标签统一使用浅色背景、彩色文字和细边框，不使用深色实心色块。

测试执行结果使用独立的 `execution_status`（未执行、通过、不通过、跳过、堵塞），不复用或覆盖 `case_status`。执行页只读展示用例状态，并将每次结果关联到冻结的 Case Revision。

## 4. 模型选择规范

- `auto`：平台根据任务复杂度、数据策略和可用 Provider 路由。
- `pro`：复杂需求、风险识别和高质量结构化用例。
- `local`：仅使用本地推理服务；不可用时必须阻止提交或要求用户切换，不能静默改用云模型。
- 每次任务保存 `model_id`、最终 Provider、最终模型版本、参数、提示词版本和输入来源快照。
- 模型切换只影响后续任务，不改变历史生成结果。

| 优先级 | 风险 | 处理基线 |
|---|---|---|

| P0 | 提交评审仍是占位交互 | M4 完成评审面板和权限 |
| P0 | `local` 模型不可用时尚无提交阻断 | Provider Adapter 接入时实现能力探测 |
| P1 | 生成取消、重试和断点恢复未完成 | M3 检查点与幂等任务 |
| P1 | 文件上传只有前端队列 | M2 对象存储与解析管线 |
| P1 | 测试说明发布和多格式导出未完成 | M5 |
