## 本轮真实补齐验收：不通过

在临时测试账户内预置 17 条正式登录用例，通过真实 API、模型和当前代码 worker 执行“17个case太少了，增加到30个，已有用例保持不变”。两次运行分别耗时 125.694 秒、114.609 秒，均新增 0 条。

第二次诊断确认生成任务状态为 `awaiting_input`，问题编号为 `case_allocation_conditions`，提示：“为保持现有测试点并生成13条不同用例，请补充各条用例应覆盖的具体条件或路径。”

结论：数量差额正确，生成阶段仍被场景分配规则阻断，未实现用户期望的直接补齐。相关规则要求场景差异逐字来自原始需求，且每个已确认测试点均须被覆盖。不能通过取消数量校验或复制用例凑数来让验收变绿。

限制：本轮预置的是正式用例，尚未复现原会话的候选用例状态；原用例不变断言在数量断言之后，未执行，不计为通过；没有进行跨轮语义去重或连续操作综合验收。测试账户已清理，用户原会话未改动。

证据：`artifacts/semantic-acceptance/topup-workflow.json` 与 `artifacts/semantic-acceptance/topup-diagnostic.json`。本轮相关基础回归 17 项通过，但不改变端到端验收失败的结论。

修复了“每个差异条件必须逐字来自用户原文”的限制：新增 `confirmed_point` 设计依据，允许在已确认点范围内设计等价类、边界、输入组合及操作路径；原文引用仍保持原校验，独立模型审核仍检查是否编造业务规则。分配阶段提供已有用例摘要以帮助避免重复。

真实 API + 当前 worker + 模型重测通过数量与保留校验：17 条正式用例保持不变，新增 13 条候选用例，合计 30 条，生成任务 completed。耗时 213.930 秒。证据：`artifacts/semantic-acceptance/topup-allocation-repair.json`。相关分配、数量、分批生成测试 145 项通过。

本次只验证正式资产补齐路径。输出 grounding_status=unverified，包含 manual_review_required；生成规划涉及记住密码、验证码、锁定等需确认的产品能力，因此不将数量通过当作业务准确性通过。语义去重、原会话候选保留和整体性能仍不能宣称完成。未部署或修改原会话。

## 全链路审查修复与候选补齐验收

本轮修复：

- 数量契约增加范围资产 ID、保留已有候选标记及是否包含复用输出的语义；程序校验范围 ID 并计算实际输出预算。
- 复用同一来源仅占一个输出位置；同一来源的不同修改方案各占一个位置。复用去重产生缺口时走场景分配，最终数量不符不能标记成功。
- 删除创建生成任务时提前归档全部候选的逻辑，规划失败也保留原工作。
- 保存阶段区分追加与替换；追加保留旧快照、版本和编号，编号冲突时新候选使用独立编号。
- 数量预算通过生成结果传入保存阶段；完成结果 total_count 使用用例数，不再使用测试点数。
- 场景审核允许使用用户已确认测试点中的条件，仍禁止添加确认范围之外的业务规则。失败澄清保留具体原因。
