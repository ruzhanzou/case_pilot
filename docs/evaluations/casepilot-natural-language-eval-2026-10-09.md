## 1. 使用方式与数据基线

同名 JSON 是机器可读候选集合，每条含稳定ID、优先级、测试点引用、输入轮次、交错动作、四段式正文及场景断言；本 Markdown 是执行指南。多轮输入不是一次拼接提交，必须按场景动作在轮次间执行采纳、拒绝、故障等操作。默认用真实浏览器、API、worker、模型和独立数据库/队列执行；故障注入仅用于标注的恢复场景，并记录注入时点。不能把模拟模型测试当成真实模型能力验收。

- **F**：每个场景复制一个独立集合，正式用例 A=`TC-LOGIN-01`（短信登录，模块`登录/短信`，P1）；B=`TC-LOGIN-02`（密码登录，`登录/密码`，P1）；C=`TC-PAY-01`（支付成功，`支付/付款`，P1）；D=`TC-REFUND-01`（退款成功，`支付/退款`，P2）。全部启用；保存真实ID和版本号，不能按显示位置断言。A步骤含“输入短信验证码并提交”，B不含该词。默认A/B/C/D分别有1步及可观察验证；场景指定长步骤时用编号动作和验证扩充。
- **编号隔离补充（实测校正）**：F中的编号为逻辑别名。同一空间中编号唯一，每次运行追加唯一后缀并将自然语言中的编号同步替换，保存映射。跨集合相同编号隔离场景须使用两个有权限的空间，不能在同一空间强行创建重复编号。
- **CAND**：独立空正式集合，先用下述测试需求生成3条候选，分别覆盖正确、错误、过期验证码，并补充合成规则“错误验证码不得建立会话”；按场景含义记录实际候选ref为K1/K2/K3。自然语言中的K2等必须替换为界面可识别的真实候选编号，不把别名直接发给产品。候选基线及版本单独保存。
- **R-LOGIN（合成测试需求，不是产品真实业务承诺）**：①已注册且启用账号使用正确密码可登录并建立会话；②错误密码不得建立会话；③正确短信验证码自签发起`t<120秒`有效，成功建立会话；④`t≥120秒`失效，提示过期且不建立会话；⑤已成功使用的验证码再次使用被拒绝且不建立新会话；⑥退出后旧令牌访问受保护资源被拒绝。每条规则编号R1至R6，时间边界使用可控时钟。
- **大数据集**：正式资产通过fixture/API创建，避免把准备时间混入性能计时；生成性能场景使用独立测试点作为输入。1000条场景50个模块M01至M50，每模块20条，每条唯一编号。20/21/25/100为分批边界组；1000条是探索容量档，非既有容量承诺。
- 每个场景留存 before/after 全集合快照；建议阶段另存 proposed_snapshot、field_diff、target refs、base versions。若权限角色、取消入口或测试环境不具备，记录 BLOCKED 或能力缺口，不跳过后计通过。

## 2. 公共判定规则

1. **范围**：实际目标ID集合等于期望集合，既不能多也不能少。不能把只处理第一页或首批算全部完成。显式条件、否定词、排除项及当前集合边界均必须保留。
2. **变更**：确认生成建议、采纳修改、纳入候选是不同动作。正式资产只能在对应写入确认后改变；候选修改的采纳仅更新候选，纳入才创建正式资产。删除须按删除确认边界校验。
3. **保真**：未授权字段及非目标资产保持相同；只对实际有效修改创建版本。排除预期审计时间变化后比较业务字段，同时单独核对版本、资产数量和审计事件。拒绝、取消、无改动不能新增有效正式版本。
4. **正文**：新生成用例遵守项目四段式规范，1至4个动作且验证逐项对应；已有用例改写应保留合法历史结构，包括空前置和5至100步，不能套用新生成限制压缩历史资产。
5. **语义**：精确赋值做字段等值比较；语义重写由QA依据业务规则逐条判断。仅出现“断网/重试”等词不算满足，必须同时有可执行操作、可观察结果和正确因果顺序。模型评分只能辅助，不作唯一裁决。
6. **澄清**：`PASS`=独立满足全部断言；`SAFE_CLARIFY`=未误操作但需额外澄清，准确执行能力未通过；`FAIL`=断言违反；`BLOCKED`=环境/依赖阻塞；`NOT_RUN`=未执行。以澄清为预期的场景正确澄清可PASS；确定目标却反复澄清记易用性失败。unsupported明确记能力缺口。
7. **时间和终态**：轮询结束不等于任务成功。核对所有依赖操作和落库结果；运行、待确认、完成、失败、取消、冲突分别记录。首次失败后重试成功记 recovered，不能抹掉首次失败。

## 3. 评分、门禁与性能建议

以下是建议验收门槛，尚非已确认产品SLA。先记录基线再决定发布门禁。

分开统计明确赋值快捷路径与模型语义改写。记录模型/版本、参数、token、调用数、重试、队列并发、机器规格、网络、数据规模和commit。每个性能档先3次预热不纳统计，再至少30次有效样本，报告p50/p95/max及失败率；p95用升序第ceil(0.95×N)项。失败及超时不能从报告消失：耗时分布注明成功样本数，另报失败、超时、取消及端到端截止时间。1000条高成本档可先5次探索，只报原始值/范围，不据此声称稳定p95。模型限流与应用耗时分解记录。

自然语言稳健性：优先对GEN-11、SCP全组、EDT-05、MUL全组做每场景至少3次独立重复；另取书面/口语/中英混合/编号引用四种等义表达。能力分母不能混入有意歧义场景。保留10个未参与调优的改写表达作为回归盲测集，固定输入、fixture和判定规则后再执行。

## 4. 执行顺序与证据

先跑冒烟：GEN-01 → MUL-06/07 → EDT-01/05 → MUL-01/04/05 → REV-03/04/07 → REC-01/06；各场景独立fixture，箭头仅表示执行顺序。然后跑全部功能和恢复集，再性能档和真实QA易用性观察。不要在真实用户集合做故障注入或压测。

每次运行保存 `run_id/case_id/repeat/commit/model/fixture_id/conversation_id/job_ids/change_set_ids/实际输入/目标ID/前后快照/阶段时间/请求响应/截图或trace/逐条断言/结果/失败归因`。文本与日志去除凭证。结果模板见同目录JSON；记录未执行、能力缺口、基础设施故障和产品缺陷，不能混成同一个通过率。
