# 大附件规划性能优化（2026-10-11）

## 改动

- 多分片附件使用 `PlanningAnalysis`，在同一次模型调用中提取需求和功能，省去第二遍全文读取。单分片维持原链路；未返回功能的分片单独回退。
- 同一文档中，原文可验证、定义无冲突的同编号规则使用一致分类，避免模型跨分片命名差异导致重复功能。合并保留各分片的描述、约束及来源。
- 每个测试点功能组仅发送匹配原文的引用及附近上下文，保留完整已提取需求。允许冒号宽度及句末标点差异，返回内容始终截取自原文。任一引用核验失败、压缩反而变大时回退完整上下文；完整原文仍保存在规划中。
- Ark 的 `requirement.extracted` 阶段关闭额外推理；测试点设计、用例生成和独立审核保持原设置，其他供应商不接收此参数。
- 需求与功能一起保存检查点；恢复时复用提取结果，仍校验测试点数量和功能覆盖。

## 测试口径

同一份 1 MiB TXT（1,048,576 字节，非填充内容 1,045,978 字节），SHA-256：
`03245caa0a1d8e3e75254159bbc4d1fd83df392104913edcff8916698e75a32b`。

附件包含登录、订单、退款三个模块的 18 条规则和大量重复样例。使用真实 API、附件解析、`doubao-seed-2.0-lite`、规划确认、用例生成、审核及候选落库；各次运行使用独立测试账户与任务，不跨任务复用模型结果。

历史版本数据来自上一轮最终有效检查点，不包含此前失败和废弃结果。历史端到端 31 分 49 秒包含人工中断、修复和重试，不能作为稳定耗时基线。以下 token 对比只统计规划，不重复计入汇总的 `requirement.analyzed` 记录。

| 规划指标 | 历史版本 | 本次最终版本 |
| --- | ---: | ---: |
| 需求提取调用 | 32 | 32（同时提取功能） |
| 单独功能提取调用 | 32 | 0 |
| 测试点调用 | 21 | 6 |
| 合计调用 | 85 | 38 |
| 累计输入、输出 token | 1,978,622 | 649,391 |
| 功能 / 测试点数量 | 55 / 55 | 18 / 18 |

规划调用减少 55.3%，token 减少 67.2%。所有 32 个资料分片均被处理，没有按文件头截取或抽样跳过。最终运行的 68 个合并前功能组都通过引用核验；这些组携带的原文累计从 1,072,126 字符缩小至 84,974 字符。该字符统计发生在组间合并之前，不等同于最终请求 token。

另做同一分片的提取对照：保留额外推理时约 56.9 秒，关闭后模型计时约 18.6 秒（包含调用初始化约 19.3 秒），保留了全部 6 条规则和关键数值。这只是单批实验，不代表全链路加速倍数。

## 验证

- 最终冷运行完成 18 条候选用例并落库，18 个规则编号各覆盖一次，所有用例引用都链接到原始资料分块。
- Agent 回归：181 项通过。
- 原文引用匹配、标点兼容、引用失败回退、不同文档与冲突定义、合并后覆盖、断点重试均有回归测试。
- 最终规划只读重放：0 次新增模型调用，约 2.08 秒，与持久化规划完全相同。
- 本地运行容器的规划、任务与供应商代码哈希已与工作区核对一致。

## 实测时间与质量限制

| 计时项 | 本次中间对照 | 最终版本 |
| --- | ---: | ---: |
| 附件就绪 | 13.35 秒 | 12.32 秒 |
| 请求路由 | 14.10 秒 | 18.85 秒 |
| 需求、功能、测试点规划 | 566.86 秒 | 373.31 秒 |
| 确认后生成与审核 | 143.87 秒 | 119.15 秒 |
| 完整链路单调计时 | 739.73 秒（12 分 20 秒） | 524.97 秒（8 分 45 秒） |
| 完整链路挂钟时间 | 785.07 秒（13 分 5 秒） | 642.04 秒（10 分 42 秒） |

中间对照已使用一次提取和初版引用压缩；最终版本再加入提取阶段关闭额外推理、按功能组压缩和标点兼容，单调计时减少约 29%。这不是相对历史旧版本的端到端加速比例，也不能归因于某一个单独改动。运行环境的单调计时与挂钟时间存在差异，此处保留两者，不推断差异原因、不混用计时口径。最终测试没有人工中断、部署切换或任务级重试。

人工语义检查未完全通过，代表性问题如下，原始候选未被手工修饰：

- `LOGIN-1 / LOGIN-2` 增加了原文未规定的跳转、停留页面及提示文案。
- `ORDER-1` 使用“状态正确”这类不明确的预期。
- `ORDER-3` 额外要求重复请求返回既有订单信息；原文只要求生成一个订单。
- `REFUND-4` 额外要求拒绝重复请求；原文只要求处理一次。
- `ORDER-4` 等待步骤的逐行预期为空。按产品现有“操作与用例级校验可分列”的契约，18 条用例均有操作和校验；按此次测试提示词的严格逐步配对要求，此项未通过，原始报告保留 `all_steps_complete=false`。

因此本次确认的是性能改动有效、链路完成、规则与引用覆盖完整，不宣称生成内容已全部达到可直接采用的质量。

## 复现与证据

```bash
python scripts/qa/attachment_performance.py --label final --output output/attachment-compact-20261011
PYTHONPATH=apps/agent/src .venv/bin/pytest apps/agent/tests -q
```

原始记录保存在 `output/attachment-compact-20261011/`：`compact.json` 为本次中间对照运行，`final.json` 为最终冷运行，`final-replay.json` 为检查点重放，`final-metrics.json` 为阶段调用统计，`summary.json` 为验收汇总，`generated-cases.json` 与 `semantic-issues.json` 保存原始候选和人工问题。大文件、完整模型输出和测试账户记录不提交到仓库。

这是一份规则重复率很高的合成附件，不代表 1 MiB 全部不同需求、PDF/OCR 或多用户并发场景。覆盖编号、结构校验及模型自动审核通过，也不等于全部业务断言均得到原文支持。
